# About this fork

HearthDAoC (`lometur/HearthDAoC`) is an unofficial fork of [shadowofze/OfflineDAoC](https://github.com/shadowofze/OfflineDAoC).
It runs OfflineDAoC as a central multiplayer server and keeps its own changes small and additive,
so upstream updates merge cleanly.

The fork was renamed from its working title ("OfflineDAoC central server fork") to HearthDAoC on
2026-10-05, before its first release. The sub-project 1 spec, plan and verification record keep the
old names (`odc`, `OFFLINEDAOC_*`, `offlinedaoc-*`) as written at the time.

## Client patches

The patch set `client/patches/classic-creation.json` gives the OfflineDAoC 0.35 classic client a classic
character creation screen and the HearthDAoC loading splash (sub-project 2, see
[its spec](specs/2026-10-06-classic-character-creation-design.md)). The patch set
`client/patches/default-layout.json` gives new characters a window layout (The default layout, below). The
patch sets `client/patches/si-portals.json` and `client/patches/si-portal-art.json` take upstream's Shrouded Isles
portal art out of the 1.74 town spots and give the Albion portal its 2002 look (The Shrouded Isles portals,
below). All hold only SHA-256 hashes, byte and text edits and our own code, never an EA file. The launchers apply
each at every launch, just before the game starts, in that order, so files that something put back (a repair,
OfflineDAoC's own launcher, an update) are patched again:

- Linux: `setup.sh` installs the bundle's `patches/` (`apply_patches.py`, `patchset.py`, `classic-creation.json`,
  `default-layout.json`, `si-portals.json`, `si-portal-art.json`, `splash.mpk`) as `<dest>/patches`, a fresh copy
  on every run, and applies each set from there. `play.sh` runs `<dest>/patches/apply_patches.py` once for each set
  before every launch.
- Windows: `connect-hearthdaoc.bat` runs `patch-client.ps1` (`client/windows/`, same rules as the Linux
  applier) from its own folder once for each set before every start of `connect.exe`. `patch-client.bat` runs it
  by hand, once for each set with the player's options (`-Restore`, `-Check`), or once for the set `-PatchSet`
  names; for example once as administrator when the install is under Program Files.

A refusal is all or nothing for a set, so each set is applied by a run of its own and reported on its own: one
refused or failed never stops the others (the b edition's client gets the layout, and a `default.ini` changed by
hand doesn't stop classic creation). A set with `"retired": true` is restored instead of applied by a run without
`--check` / `-Check`, so a release takes a set back with no launcher change (The Shrouded Isles portals, below). An
already patched client is only read. Exit 3 (a client file the set doesn't know) starts the game without that set,
with one line on Linux; any other failure warns and still starts it. Without the installed patches
(`<dest>/patches`, or `patch-client.ps1` next to the .bat), or without a set's JSON, the launchers don't apply it:
that is how a player opts out of a set, after a restore of it (the player guide says how). Both appliers refuse any
other client file, such as the b edition's `game.dll` or an older or newer upstream client's, and then change
nothing. Both keep each original as `<file>.hearthdaoc-orig` and put it back with `--restore` / `-Restore`, but only
over the patched file: when a file has changed since it was patched (for example a newer upstream client), the
restore says so and changes nothing. A set's optional `"refused"` text is what follows "Not patched: <file> is not
the file this HearthDAoC release supports " for a refused file (which clients those are, and what the player gets
instead); without it, the appliers print classic creation's.

**Rebuilding the patch set.** `classic-creation.json` is generated, never edited by hand. Rebuild it after a
change to anything above, to the server's class files or to `deploy/upstream.lock`. CI rebuilds it on every run
from the pinned release's files and fails ("Client patch set matches a rebuild") when the committed file
differs. A change to the generator alone (`build.py`, `pe.py`, `classdata.py`, `src/`,

The archive paths are the lock's `editions.classic` and `client_prefix` (the world database is about 90 MB; for a
release built on an upstream patch it is the base release's world, whose `disabled_classes` the rebuild reads).
The tests skip the real-file cases without `HDC_CLIENT_FILES` and `HDC_TEST_WORLD`, the MPK cases without
`HDC_MPK_TOOL` (the `OfflineDaoc.Mpk.dll` built for the splash above) and the PowerShell cases without `pwsh`
(or `HDC_PWSH`). CI sets all of them; `ClientPatchWorkflowTests` in `deploy/tests/test_workflows.py` (needs
ruby) keep the workflow that way. `setup.sh` run from a checkout installs `client/patches/` (with the committed
`splash.mpk`) as `<dest>/patches` and applies it from there.

If the pinned release's classic `game.dll` changes, `build.py` refuses it until the patch sites in `build.py`,
`classdata.py` and `src/baseclass.asm` are found again in the new file. Until then CI fails and players with
the new client keep the standard creation screen. A new upstream section moves `.hdcc` to a new address (0.35
added `.bounty`): `ORG` in `client/patches/tests/test_cave.py`, the section list in `test_pe.py` and the header
offsets in `test_build.py` pin it, so update them with it. Players must then update their client: a `game.dll`
of the old release, patched or not, is unknown to the new patch set (see the
[v0.35b-hearth.1 release notes](https://github.com/lometur/HearthDAoC/releases/tag/v0.35b-hearth.1)).

**Changing the `game.dll` patch later.** Players' clients stay patched by the release they had, and the
launchers apply the new release's patch set at the next launch. A `game.dll` patched by an older patch set is
neither "before" nor "after" for the new one, so both appliers would refuse it (exit 3, nothing changed: the
player keeps the old patch and is told the client isn't supported), and a restore would refuse it as changed
since it was patched. The same holds for any patched file whose "after" changes. Such a change must also teach
both appliers to upgrade: recognise the older patched file, put its verified backup back, then apply the new
set.

### The default layout

When a character has no settings file (`<FirstName>-5.ini` in the profile folder, on Windows
`%APPDATA%\Electronic Arts\Dark Age of Camelot\<profile>`), the 1.127 client (EA's code, the same in stock
`game1127.dll` and in our `game.dll`, at `0x4c5fe9`) takes its layout from the client folder's `default.ini`: the
section `[Panels-<width>x<height>]` for the screen size, and `[Quickbar]` to `[ToolTips]` from the first section of
each name in the file. It writes the character's own file the first time the character leaves the world
(`0x4c1163`), and reads that from then on. The server stores no layout, hotkey or macro.

`default-layout.json` puts one block in front of `default.ini`'s first line, `[Panels-800x600]`, so each of its
sections is the first of its name: the owner's character Charles Martel's `[Panels]` as `[Panels-1920x1080]`
(every key in the client's order; the looking-for-group keys, which follow the character's level, at a new
character's values), empty quickbars (`GroupSize=10`), `[Macros]`, `[QuickBinds]` and `[HouseHelp]`, and that
character's `[Chat]`, `[NameOptions]`, `[Camera]` and `[ToolTips]`, in CRLF lines as the client writes them. A
new character at 1920x1080 starts with that layout and empty quickbars; at another screen size, with the stock
layout (the 26 stock blocks stay below) and our name plate settings. `default.ini` is the same EA file in both
OfflineDAoC 0.35 editions (the release manifest pins it once, `f43e1b5d…`), so the set supports both. The set
carries the 18-byte anchor line, as `classic-creation.json` carries `from` bytes, and nothing else of EA's.

**Rebuilding it.** `client/patches/layout.py` (the generator) reads a character's settings file and OfflineDAoC
0.35's `default.ini` (it refuses any other) and writes the set; twice gives the same bytes. Charles's file is in
the owner's profile folder, not in the repository: when the owner changes that character's layout, rebuild and
commit the JSON (a release then offers it as a client update; Linux players get it at their next launch after
accepting).

```bash
c="$(mktemp -d)"  # an EA file from the pinned release, verified; never commit or share it
python3 tools/linux/odaoc_fetch.py --lock deploy/upstream.lock extract runtime/client-opendaoc/app/default.ini "$c/default.ini"
python3 client/patches/layout.py --from "<profile folder>/Charles-5.ini" --client "$c" --out client/patches/default-layout.json
HDC_CLIENT_FILES="$c" HDC_LAYOUT_FROM="<profile folder>/Charles-5.ini" python3 -m unittest discover -s client/patches/tests -t client/patches
rm -rf "$c"
```

CI fetches `default.ini` with the classic files (into `HDC_CLIENT_FILES`), and `test_layout.py` then checks the
committed set against it: its hashes, the client's lookup for a new character, apply, re-apply and restore, and
that `layout.py` rebuilds the same file from the set's own block (so a hand edit, or a block that breaks the
rules, fails). `HDC_LAYOUT_FROM` adds the check against Charles's own file: the same set, and a new character
reads every value of that file but the hotkeys and the looking-for-group level range. Only 1920x1080 has the
layout (other sizes would need scaled blocks: untested). Not yet checked in game.

### The Shrouded Isles portals

The server has the three portals at their 1.65 spots (the server-code row "The Shrouded Isles portals at their
1.65 spots"), so the client art upstream 0.35 added at the 1.74 town spots marks a portal that takes no one
anywhere. Upstream's tool (`tools/claude-version/si_portal_visuals.py`) appended one fixture row and one nif row,
each named `SI Portal Visual <zone>` and each the last line of its entry, to each realm's home zone archive, and
repacked it:

- `si-portals.json` takes those six rows out again: two `mpk-text-replace` operations per archive, on
  `zones/Zone000/csv000.mpk` (`fixtures.csv`, `nifs.csv`), `zones/zone100/csv100.mpk` (`FIXTURES.CSV`,
  `NIFS.CSV`) and `zones/zone200/csv200.mpk` (`fixtures.csv`, `NIFS.CSV`). Each entry is then the base client's
  (82685, 4383, 46233, 4506, 87013 and 6029 bytes); every other entry is kept byte for byte.
- `si-portal-art.json` moves `Newtowns/zones/Nifs/bavteleporter.npk` (the 2006 remake, which the client loads
  before `zones/Nifs`) aside with a `remove` operation, so the client loads `zones/Nifs/BAvTeleporter.npk`, the
  2002 model with its purple flames, wherever the Albion portal model stands (after the first set, only at
  Caer Gothwaite). Our client has no 2006 Midgard or Hibernia portal model: those are 2002 already.

Both sets hold only the six rows (the text to remove, from upstream's tool), the four files' hashes and the
`remove` operation; the rebuilt archives are made on the player's machine from the player's own files. Every
edition gets both: the zone files are the same in `classic` and `b`.

**The operations** (format 1, in both appliers; `patchset.py` holds the archive code, so the bundle's file list
stays the same, and doesn't import `mpk.py`):

- `{"op": "mpk-text-replace", "entry": ..., "find": ..., "replace": ...}`: the bytes must be an MPK archive; the
  one file in it named `entry` (exactly, case included: the archives differ) gets `text-replace`'s edit (on its
  content as Latin-1, `find` exactly once). The archive is then rebuilt the same way every time: the header
  (`MPAK`, the byte 2, then the directory's CRC-32 and compressed size, the name's compressed size and the file
  count, each byte XORed with its index) is written anew; the compressed archive name is copied; every other
  file keeps its compressed bytes, CRC-32, 256-byte name field (bytes after the NUL included), timestamp and
  flags; the edited one keeps its name field, timestamp and flags and is written as zlib stored blocks (`78 01`,
  blocks of at most 65535 bytes, each `BFINAL`, `LEN` and `~LEN` little-endian and the bytes, one empty block for
  no data, then the Adler-32 big-endian) with its new size and CRC-32; every record gets the running total of the
  earlier files' sizes as `mem` (as upstream's packer writes it) and its offset, the files following each other
  in directory order; the directory is written as stored blocks too. Only the CRC-32 of the directory and of the
  edited file are checked: the `before` hash pins the rest. A second operation on the same archive copies what
  the first wrote, so two give the bytes of one rebuild with both edits.
- `{"op": "remove"}` with `"after": "absent"` (its only operation): the file is renamed over
  `<file>.hearthdaoc-orig`, never written; a missing file counts as patched, also on a client that never had
  it; a restore renames a verified backup back where the file is missing. A present file with another hash is
  refused (exit 3), and a restore refuses one ("changed").
- `"retired": true` (a set-level boolean): a run without `--check` / `-Check` restores the set, as `--restore` /
  `-Restore` does; `--check` still reports the patch states.

**Why stored blocks.** The appliers must write exactly the bytes the `after` hash pins, on Linux (Python's zlib)
and on Windows (PowerShell 5.1 on .NET Framework, whose `DeflateStream` compresses differently from zlib).
Stored blocks are the one zlib encoding both write byte for byte alike, and every inflater reads them (the
client too, which the owner's in-game check shows: the three home zones load). The cost is size: the
three archives grow about 3.6 times (25086 to 91119, 14670 to 53841, 26361 to 96194 bytes), which is harmless. The prototype that settled the encoding
(`~/tmp/hearthdaoc-period/scripts/repack_proto.py` on the owner's machine, 2026-10-22, in memory on the player's
own files) gave the after hashes the committed set pins: `41976bf7…`, `d5e7552a…`, `7406b52d…`. The appliers'
tests (`test_appliers.py`, both appliers) check the same bytes at the 64 KiB block boundaries, and
`test_build_si_portals.py` runs both appliers on copies of the real files. Those PowerShell runs use PowerShell 7
(`pwsh` on .NET 8, in CI and locally); Windows PowerShell 5.1 on .NET Framework, which players run, has not run
the archive code yet (only its syntax is checked, by `test_appliers.py`). A difference there is safe:
`patch-client.ps1` builds every new file and checks its `after` hash before the first write, so it exits non-zero
with nothing changed, `connect-hearthdaoc.bat` warns, and the game starts with upstream's town art. A Windows
client's first start that prints `Patched:` for the three archives and the model shows it works.

**Rebuilding them.** `client/patches/build_si_portals.py` (the generator; a change to it alone makes no release)
reads the four client files and writes both sets: it finds the one `SI Portal Visual` line of each fixtures and
nifs entry (in any case), requires it to be the last line with its CRLF, and takes the `after` hashes from
`patchset.transform`. CI fetches the four files with the others and fails ("SI portal patch sets match a
rebuild") when a committed set differs from a rebuild; `test_build_si_portals.py` checks the sets against the
files (`HDC_CLIENT_FILES`). The `before` hashes are the 0.36b package's
(`source/tools/release-baselines/0.36/0.36b-package.sha256`), which the 0.37 game patch keeps; OfflineDAoC 0.35's
copies were not available to compare, so a 0.35 client whose files differ is refused (exit 3: nothing changed,
the game starts with upstream's art). From the repository root:

```bash
c="$(mktemp -d)"  # EA files from the pinned release, verified; never commit or share them
for f in zones/Zone000/csv000.mpk zones/zone100/csv100.mpk zones/zone200/csv200.mpk \
    Newtowns/zones/Nifs/bavteleporter.npk; do
  python3 tools/linux/odaoc_fetch.py --lock deploy/upstream.lock extract "runtime/client-opendaoc/app/$f" "$c/$f"
done
python3 client/patches/build_si_portals.py --client "$c" --out-dir client/patches
HDC_CLIENT_FILES="$c" python3 -m unittest discover -s client/patches/tests -t client/patches
rm -rf "$c"
```

**Switching to the 2006 look** (the owner may, server-wide; there is no per-player setting) is one small release:
set `ALBION_LOOK = "2006"` in `build_si_portals.py` (and the line of `test_build_si_portals.py` that pins the
shipped look), rebuild, and commit the JSON, which then says `"retired": true`. Every client that has the set
applied gets the model back from its backup at its next start: on Linux `setup.sh` builds the client afresh at
the update (the model comes from the base client and the release, and there is nothing to restore), on Windows
`connect-hearthdaoc.bat` restores it at the first start after the player copies the release's files. Switching
back is `"2002"` again. The portals stay at the 1.65 spots either way: moving them back to the towns is a revert
of the server change, a separate decision.

**Taking the portal fix back** (if a client can't read the rebuilt archives, say Camelot Hills, Vale of Mularn
or Lough Derg fail to load: that the game reads stored blocks is the one guess here no test can check) is one
small release the same way: set `PORTALS_RETIRED = True` in `build_si_portals.py` (and the line of
`test_build_si_portals.py` that pins it), rebuild, and commit `si-portals.json`, which then says
`"retired": true`. Every client that has it applied gets upstream's three archives back from its backups, on
Linux at the update and on Windows at the first start after the player copies the release's files
(`test_build_si_portals.py` runs both appliers on the retired set). Upstream's inert portal art in the three
towns comes back with them; the server's portals stay at the 1.65 spots. A player who can't wait for that
release takes the set out by hand (client/README.md, The Shrouded Isles portals).

**Never drop a set that has shipped; retire it.** A Linux release without a set gets the client's own files back,
since `setup.sh` builds the client afresh (`test_setup.py` checks it for the art set). But nothing runs a set that
is gone on a Windows client: its files stay patched (the 2006 model stays aside as
`bavteleporter.npk.hearthdaoc-orig`) for good.

Known leftovers (#163): the in-game maps still label the portal at the town spots (the client's map files, not
patched), and the server's navmeshes keep upstream's platforms there. If the owner's pre-check P2 shows no purple
flames on the Avalon Marsh pier, the pier's global 2006 copy (`zones/Nifs/avpier.npk`) would be a second `remove`
entry of the art set, so that the client loads `zones/ZONE009/Nifs/AVPIER.npk`: not done.

## Client updates

Linux clients update at launch, after asking the player. Windows players still copy the new files by hand.

- `deploy/build_bundles.sh` writes the release tag into the client bundle's `VERSION`, and the client's content
  ID into `CONTENT_ID` and beside the bundle as the release asset `hearthdaoc-client-<tag>.content-id`: the
  SHA-256 of the bundled files' `sha256sum` lines in path order, without `VERSION`. Two releases of the same
  client have the same ID.
- `setup.sh` saves its options (`--server`, `--edition`, `--base-client`, made absolute), that tag and that
  content ID (`content_id`, empty from a checkout or an older bundle) in
  `<dest>/hearthdaoc-client.conf`, last and by a rename, so a failed setup keeps the previous release. From a
  checkout there is no `VERSION`, the tag is empty and `play.sh` never checks. It also writes `play.sh` as
  `play.sh.new` and renames it: a running `play.sh` that updates itself goes on reading its own file.
- Over an installed client, `setup.sh` builds the new one in `<dest>/client.new` (hard links to the old
  client, or a full copy where hard links fail) and keeps the old patches in `<dest>/patches.old`. It swaps
  them in only when everything worked; a failed setup, say a download that stops, leaves the install as it
  was. rsync, `odaoc_fetch.py` and the patches replace files by a rename and never write into them, so the
  hard-linked old client stays as it was. A first setup builds `<dest>/client` in place.
- At each launch, before the login, `play.sh` reads that file (never sources it) and asks GitHub's releases
  page (`.../releases/latest`, as `hdc update` does) for the newest tag, for 5 seconds at most. For tests,
  `HEARTHDAOC_RELEASES_URL` points `play.sh` (and `hdc`) at a local server instead; players never set it. It
  offers a newer tag (`sort -V`, with 0.35 before 0.35b) with a zenity or terminal question, unless that
  release's `.content-id` (fetched for 5 seconds at most) equals the saved `content_id`: a release that changes
  only the server plays on with one line on stderr. Without an ID to compare, the release is offered. Yes downloads
  `hearthdaoc-client-<tag>.zip` into `<dest>/.update.XXXXXX`, checks its `setup.sh` and that `VERSION` says
  the tag, runs that `setup.sh` with the saved options and `--dest <dest>`, then starts the new `play.sh` with
  `HEARTHDAOC_NO_UPDATE=1`. A failure warns, keeps the saved tag and plays the installed release. Before each
  update, it removes `.update.*` folders left by one cut short (a power cut). `HEARTHDAOC_NO_UPDATE=1` turns
  the check off.

So every client bundle must keep `hearthdaoc-client-<tag>/setup.sh` and `VERSION`, and every `setup.sh` must
accept the options of the earlier ones: the players' `play.sh` runs it with them. Every `setup.sh` must also
change an install only once everything worked: after a failed update, `play.sh` tells the player that the
installed release starts. `UpdateRoundTripTests` in `client/tests/test_play.py` updates a client set up by
`setup.sh` with a bundle built by `build_bundles.sh`, and fails one halfway. Every release offers a client
update, even one that changed only the server.

## Syncing with upstream

1. Sync through a PR, not GitHub's **Sync fork** button: that commits straight to `main`, and merging is
   releasing (below), so it would publish before `deploy/upstream.lock` is updated. Merge the release tag,
   not `upstream/main`: upstream's `main` can be behind its release (for 0.35b it was 33 commits behind), and
   the code must be the release's code, the commit the lock pins.
   `git fetch upstream --tags && git switch -c sync/<version> origin/main && git merge v<version>`
   Upstream's line endings keep changing (22 server files from 0.35b to 0.37b): a file the fork marks whose
   endings flipped is one whole-file conflict. Turn our side of it to upstream's new ending, merge it again, and
   keep upstream's ending. Some files upstream ships with both (v0.37b's `ClassicQuests.cs`: 14 CRLF lines in an LF
   file). The source checks (`deploy/tests/endings.py`) compare each file the fork edits with upstream's version at
   the lock's tag, line by line: upstream's lines keep upstream's endings, and each fork line takes the ending of the
   upstream line above or below it. So update the lock (step 2) before running them.
2. If upstream published a new release, update `deploy/upstream.lock` on the same branch. For a full release:
   version, tag, commit, part sizes and hashes, manifest SHA-256, edition paths and `server_files`, from the new
   release's `download-manifest.json` and `PACKAGE MANIFEST.sha256`. For a base release plus an upstream patch
   (0.37b: the full 0.36b game plus `OfflineDAoC-v0.37-game-patch.zip`): the new version, tag and commit, the base
   release's parts, manifest and edition paths at the top level, and a `patch` object for the patch zip (its URL,
   size and SHA-256 from the new release's `download-manifest.json`, its `patch.json` hash, and each edition's
   world update, `db-<version>.json`). Keep the top-level `"version"` on its own line before any nested object,
   and use no nested key named `version`: the `hdc` of the release before reads the first `"version"` line. While
   upstream ships patches on the same base, a new version changes only the version, tag, commit and `patch`; when
   it ships a new full base, drop `patch`. `ServerFilesLockTests` (`deploy/tests/test_init_world.py`) fails when
   the server source names a `classic-*.json` file that the lock does not list, or the other way round.
3. Rebuild the client patch sets (see Client patches above) and commit them on the same branch if they changed.
   A new upstream `csv000`, `csv100` or `csv200` archive or `bavteleporter.npk` fails the SI portal rebuild check:
   rebuild the two sets (The Shrouded Isles portals). If upstream took its town portal rows out itself, the
   generator finds no `SI Portal Visual` line and stops; then take `si-portals.json` out of the bundle and the
   launchers (the new release's files replace the patched ones on every client).
4. Check the fork's world fixes and hooks against the new release. Run the tests with `HDC_TEST_WORLD` set
   to the new clean classic world (for a patch release, the base release's world with the patch's world update
   applied) and `HDC_CLASSIC_QUESTS` to the new release's `runtime/server/classic-quests.json`, for a patch
   release the patch zip's (without it the classic quests' reachability tests skip): `battlegrounds.py` changes a
   row only while it holds the value it
   expects, so a changed row fails the real-data tests, and the fix then needs a new version and marker. The same
   holds for `mob_fixes.json`'s `expect` values and `start_towns.json`'s `upstream` spots (no marker: update the
   entry).
   The source checks in `deploy/tests/test_battlegrounds.py` list every fork hook in upstream files and
   every `TravelToBattleground` caller (the bots' only way in); a new one fails them until it is reviewed.
   Update the counts `deploy/HANDOFF.md` expects (navmeshes, restored spawns). A fix that finds a changed row
   can skip it without a word: at 0.37b three did (the battleground gates, the Guild of Shadows pay step and
   items), so run every world fix on a copy of the new clean world and compare what it changed with the last
   release's world, at every sync.
5. Push and open a PR; its CI builds and tests the image.
6. Merging it releases `v<upstream-version>-hearth.<n>` (a new upstream version restarts at `.1`).
7. On the server: `./hdc update` (`deploy/HANDOFF.md` → "Upgrading"). It backs up first, and for a release
   of another upstream version it upgrades the world itself. The `hdc` of the release before runs that
   update, so this starts with the update after 0.35b; from 0.34b to 0.35b, run `./hdc upgrade-world` and
   `./hdc up` by hand.

## Releases

Merging is releasing (`.github/workflows/server-image.yml`):

1. Every PR runs the full suite (docs-only PRs run nothing).
2. Every push to `main` runs the full suite on that commit (a docs-only merge runs nothing). If files that ship changed since the last
   release (`deploy/release_tag.py next`: what `deploy/Dockerfile` copies and `deploy/build_bundles.sh`
   bundles), the same run then publishes the next `v<upstream-version>-hearth.<n>` from that commit: the
   image, the tag and the GitHub release with both bundles and notes generated from the merged PRs.
   Docs, tests, CI and `release_tag.py` changes make no release. A failing test publishes nothing.
3. About 8 minutes after the merge, on the server: `./hdc update`. Linux players are offered the new
   client at their next launch (see Client updates).

The repository names no release: `deploy/build_bundles.sh` stamps the tag into the bundle's
`.env.example`, which is where `./hdc update` reads it, and HANDOFF's install step looks up the latest
release. Runs on `main` wait for each other, so releases are made one at a time. A run for a commit that
is older than an existing release publishes nothing, so re-running an old run cannot ship older code.

- To hold releases back (main still builds and tests), set the repository variable `HOLD_RELEASES` to
  `1`. Delete it, then merge the next PR or use Actions → server-image → Run workflow on `main`.
- If a release failed, a run on `main` was cancelled, or a merge made no release, fix it and merge, or
  use Run workflow on `main`: it releases everything shipped since the last release.
- Do not push `v*-hearth.*` tags by hand: nothing builds them, and the next release counts from them.
- Merging and Run workflow on `main` publish to the servers, so only the owner does either.

Each release `v<upstream-version>-hearth.<n>` publishes the image `ghcr.io/lometur/hearthdaoc:<tag>` and
attaches two assets: `hearthdaoc-deploy-<tag>.tar.gz` (compose file, `.env.example`, `hdc`, handoff) and
`hearthdaoc-client-<tag>.zip` (player scripts, the client patch set with both appliers, our `splash.mpk`, and
`VERSION`, the tag).
Neither contains EA game files. The release notes credit OfflineDAoC for the splash art.

The releases are the fork's changelog: each release's notes list the PRs merged since the release before
(`--generate-notes`), and each PR says what it changes. Upstream's own changes are in `CHANGELOG.md`.

Each release's notes also say what to do to update, in a "To update" section just before "What's Changed":

- **Owner:** `./hdc update`, plus anything else the release needs: a new `.env` setting, a world fix's line to
  check with `./hdc fixes` (the last start's world fixes; `./hdc logs` has lost them by then), a command to run
  once.
- **Players:** what they do, if anything: run `setup.sh` again, accept the update `play.sh` offers, or copy
  the new Windows files.

Each PR that ships files has its own "To update" section. CI publishes the release with the generated notes
only, so after it does, add the merged PRs' sections to the release notes
(`gh release edit <tag> --notes-file <file>`). For an example with more than the usual steps, see
v0.35b-hearth.1.
